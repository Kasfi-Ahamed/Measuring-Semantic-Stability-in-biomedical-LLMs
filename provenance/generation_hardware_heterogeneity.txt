GENERATION HARDWARE HETEROGENEITY -- a reproducibility limitation of the published results
Recorded 2026-11-11.

DECODING CONFIGURATION, from notebooks/02_concept_inference/MedMentions_generative_inference.ipynb:
  do_sample=False              # greedy, T=0
  max_new_tokens=16            # CAUSAL_MAX_NEW_TOKENS
  bf16, device_map="auto"
  NO torch.manual_seed, NO torch.use_deterministic_algorithms, NO cuDNN/CUBLAS determinism flags
  anywhere in the generation path. The only seed=42 is the instance-index shuffle in cell 4,
  not generation.

Greedy decoding consumes no RNG, so a seed would not help. The exposure is different: greedy
argmax can flip on near-ties when floating-point reduction order differs, and reduction order
differs across GPU architectures. So the card matters even at temperature 0.

THE PUBLISHED MEDMENTIONS GENERATIONS SPAN SIX CARD TYPES ACROSS THREE GPU GENERATIONS.
CORRECTED 2026-11-11. An earlier version of this file said THREE card types, established from
sacct for the blocks 0-19 Llama-3 inference window alone. That window was not the whole published
set. Resolving every (model, block) pair through sacct's NodeList and sinfo's gres -- which
covers all 202 pairs with none unresolved, rather than the 81 logs that happen to carry a
DEVICE OK line -- gives SIX card types for the blocks 0-19 generative set:

  NVIDIA A100-PCIE-40GB                65 pairs    Ampere
  NVIDIA RTX 4500 Ada (24GB)           16 pairs    Ada Lovelace
  NVIDIA L40S (48GB)                   12 pairs    Ada Lovelace
  NVIDIA RTX 4000 SFF Ada (20GB)        3 pairs    Ada Lovelace
  Tesla V100-PCIE-32GB                  3 pairs    VOLTA
  NVIDIA RTX 6000 Ada (48GB)            1 pair     Ada Lovelace

The Volta card matters most. V100 is two architecture generations from Ada and one from Ampere,
with different tensor-core behaviour and different reduction ordering, so it is the least likely
of the six to reproduce another card's output token for token.

The full per-pair table is provenance/generation_hardware_by_model_block.csv: corpus, block,
tier, model, job id, node, card, job state, start, end, elapsed, and the source log, for all 202
resolved pairs across blocks 0-25. Six pairs are absent because block 25 was still running when
it was written.

Blocks 1, 2 and 5 fall outside that sacct window; their markers are dated 09-09 to 09-11 and the
jobs either predate it or ran under another job name. The conclusion does not depend on them.

CARD TYPE VARIES AT THE MODEL-BLOCK LEVEL, NOT THE BLOCK LEVEL.
This is the granularity that matters, and block 24 demonstrates it within a single block. Its
five generative models were produced on THREE different architectures:

  gen_llama3_shard0024.csv        RTX 4500 Ada      g24-2gpu-2   job 48124
  gen_biomistral_shard0024.csv    L40S              g46-1gpu-1   job 37708
  gen_flan-t5-base_shard0024.csv  L40S              g46-1gpu-1   job 37707
  gen_openbiollm_shard0024.csv    L40S              g46-2gpu-2   job 50303   (2026-11-11)
  gen_mistral_shard0024.csv       RTX 6000 Ada      g48-1gpu-1   job 50304   (2026-11-11)

So "block 3 was produced on an RTX 4500" is the wrong shape of statement. The unit of hardware
provenance is the (model, block) pair, because each pair is one job and the scheduler places each
job independently. A reviewer asking which card produced a given number needs the model-block
cell, not the block.

Nothing records this. The .complete.json markers carry path, sha256, rows and expected_rows but
no node or card, so hardware provenance has to be recovered from job logs -- which is how the
table above was built, by grepping "RUN gen <model> shard <n>" and the adjacent DEVICE OK line
across logs/. If the logs are lost, the card is unrecoverable. Adding node and GPU name to the
marker is a one-line change that was not made, and it is the right fix.

The 2026-11 rerun added L40S and RTX 6000 Ada to the set of architectures in the corpus. Block 23
ran on RTX 4500, which was already present via block 3.

WHAT THIS MEANS, stated for a reproducibility statement rather than buried:
Exact regeneration of a MedMentions generation requires the same GPU architecture that produced
it. Re-running block 7 on an L40S will not necessarily reproduce the A100 output token for token,
even with identical weights, identical prompts and greedy decoding, because no determinism flags
were in force. The effect is confined to near-ties, so aggregate statistics are robust; per-row
byte equality is not guaranteed.

This is a limitation of the PUBLISHED work, not of the rerun. It was found only by asking what
the hardware was doing, which nothing in the pipeline reports.
